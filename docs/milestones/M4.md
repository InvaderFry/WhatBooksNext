## Part 1: series and gaps (PLAN.md §7, §8, §12.5, §13.3, §13.4)

### What was built

- **Series have their own rows** (`identify/series.ts`, `syncSeries`). They're rebuilt from what's
  already stored, with no requests and no file reads. The rebuild runs after every scan, lookup run,
  restore, match decision and series correction, and at start-up. Its sources, best first:
  - the owner's correction;
  - the file's own series (EPUB calibre/EPUB 3 series, ComicInfo, filename);
  - a source's series. This is used only when the match is certain, confirmed by the owner, or
    backed by the EPUB's own ISBN, because a wrong series would invent gaps.

  A series keeps its id while its key (books vs comics/manga, plus its normalised name) stays the
  same, so corrections survive rescans. Series nothing belongs to are removed, unless the owner
  corrected them.

- **Publication status and length:** sources are preferred in the order Hardcover → AniList →
  others. A stated number of installments is kept only for a finished story. The owner can say
  finished or ongoing (`series_user`). That always wins, and "Go by the sources" undoes it.
- **Gaps** (`lib/series.ts`, pure):
  - Volumes count from 1, so owning only volume 4 means volumes 1–3 are missing.
  - Issues count only between issues the owner has or has read, because runs often start
    part-way.
  - Numbers like 1.5 and entries with no number never make or fill a gap. Spans over 500 (a year
    used as an issue number) are ignored.
  - A gap is _not owned_ or _unavailable_ (owned, but its files are all missing).
  - A finished story's stated total gives "not owned yet: volumes 3–4 of 4" on the item page.
- **One per series:** works on the series id. Entries with no number are standalone, as §8 says.
  Volumes come before issues when a series has both.
- **Cards** (§13.3, §13.4): the scope reads "Starts a series · vol. 1 · 2 of 6 owned · story
  finished" (counting only owned entries, never ones read elsewhere). Gaps show before the owner
  starts, as text with a ⚠ icon: "Gap ahead: volume 3 isn't recorded as owned or read." The
  actions are **Continue anyway**, **I read volume 3 elsewhere** and **Fix the series**.
- **Read elsewhere:** makes a history-only entry (a `history` location, finished, date unknown).
  It fills the gap, is never recommended, and adds no finish to any year. It can be undone from
  the series list. Only such entries can be removed (`DELETE /api/items/:id`); a book with files
  or a store copy is refused.
- **Item page → Series:** the order with what you have of each entry (finished, read elsewhere,
  file missing, on an unplugged drive), the gaps with "I read … elsewhere", whether the story is
  finished and who said so, and **Correct series or number** (name, number, or "not part of a
  series"). Only what the owner changed becomes a correction, and **Let the app decide** clears
  it.
- **A manga's number is a volume,** even when its ComicInfo calls it "Number".
- **Schema:** migration `005_series.sql`, with every new column nullable. The owner's corrections
  are `user_item.series_override` / `series_position_override` and `series_user`; both are backed
  up. A backup from before version 5 restores, and its series are rebuilt from the restored items.
- **Demo:** Copperline issues 1, 2 and 4 show an issue gap. A second Clockwater book shows "2 owned"
  and the series list.

### What was built

- **Metron** (`sources/metron.ts`): single issues by series name and number, one request. Then
  each run that matches the name is read once (cached) for whether it has ended (Completed or
  Cancelled → finished; Ongoing or Hiatus → ongoing) and its issue count (kept only for an ended
  run). One request every 3.1 s. Requests per day are counted across restarts, and lookups stop
  200 short of 5,000. An exhausted burst or daily window from the headers is waited out.
- **ComicVine** (`sources/comicvine.ts`), the **fallback**: asked only when no other source found a
  usable match. Otherwise its lookup is recorded as "skipped". It finds the run by name, then the
  issue in the best five runs (two requests, one every 18.5 s). Only good answers are cached, under
  keys that never hold the API key.
- **Which sources:** single issues (not manga) go to Metron, then ComicVine. They never go to the
  book sources. Without either key they aren't looked up, as before. Collected volumes still go
  to the book sources, which rate each volume. The owner's Search and pick also offers the comic
  sources for comics.
- **Matching an issue** (`MATCH_VERSION` 7, a re-score from the cache with no new requests):
  - Series name and number must match; a different number rules a candidate out.
  - Files rarely name a writer that list answers carry, so **the year corroborates**: a year in
    the file (the filename's "(2019)", ComicInfo's Year) matching the issue's cover year or its
    run's start year counts like an agreeing author (accepted). A different year never counts
    against, because runs restart and reprints exist.
  - Two issues from one comic source are never "one work entered twice": "#1" of the 1940 run and
    of the 2016 run is a real tie when the file gives no year.
  - Book matching is unchanged: `npm run report:matches` 13 of 13, 0 wrong high-confidence.
- **Series status from Metron** reaches the series (finished, with its issue count) once the
  match is certain, through the same rule as Part 1.
- **Settings:** Metron token and ComicVine key cards (masked, Show, Remove; never in backups or
  Diagnostics). **Diagnostics:** Test Metron (three issues) and Test ComicVine (one issue, about
  20 s), with a copyable report; titles only when the box is ticked.

### Test Metron / Test ComicVine on the owner's PC (2026-11-10, title-free)

Both worked first time. The request format and response shapes match the adapters, including the
run's status and issue count, the links, and Metron's headers (`x-ratelimit-burst-limit=20`,
`x-ratelimit-sustained-limit=5000`, resets in epoch seconds). ComicVine sent no rate-limit
headers. The synthetic fixtures' shapes are therefore confirmed. They stay synthetic because the
report holds no raw answers.

But **most issues came back tied**: Metron 2 of 3, ComicVine 1 of 1, one with 28 results. That
means several runs with the same name and number, and nothing in the file to choose between
them. Two tie-breakers were added (`MATCH_VERSION` unchanged in meaning; the next lookup re-scores
from the cache):

- **More years from the file:** the folder the issue sits in ("Copperline (2019)") and
  ComicInfo's Volume when it holds a year (it's often the run's start year).
- **Same run as its neighbours:** issues of one series in one folder are one run. Once any of
  them is matched with certainty, or the owner confirms one in Needs review, the tied or
  unconfirmed issues next to it are re-scored with that run (from the cache, no requests). It
  happens at the end of every lookup run, and straight after a confirmation. Siblings pointing to
  two different runs give no hint.
- A loose issue with no year anywhere and no settled neighbours **stays tied**. That's the honest
  answer; Needs review asks.
- The test report now shows the file's years, whether the run is known from its folder, and the
  top **two** candidates with their scores and years, so a tie can be explained.

Second Test Metron, with the more detailed report (title-free):

- An issue whose file has a year (2006) was **accepted**: the year matched its run's.
- An issue with no year and one candidate stayed **provisional** (0.85), on purpose. A single
  name-and-number hit could be a same-named run when Metron lacks the real one. It's still used
  for picks, labelled "unconfirmed".
- An issue with no year and 61 results (a popular name) was a **tie** between runs scoring 0.85
  each. Only a year, a settled neighbour or the owner can choose. The new tie-breakers act on the
  full run, not on this three-issue test.

## Part 3: collected editions and their issues (§12.5, scenarios 4 and 20)

- **`collection_coverage`** (migration `006_coverage.sql`, backed up): a collected edition holds
  issues first–last of a series. Each row is _suggested_ (a source says so; replaced by later
  lookups), _confirmed_ (by the owner, or typed in) or _rejected_ (never suggested again).
- **Effects, from confirmed coverage only, and only when the owner has the collection:**
  - its issues fill gaps, and widen the run that gaps are counted in;
  - finishing the collection makes its covered issues read **"via collection"**;
  - reading every covered issue makes the collection read **"via issues"**, so it isn't
    recommended.

  The "via" states are worked out each time (`lib/coverage.ts`, pure) and never written to
  progress. Every reading is counted once, where the owner marked it. A test checks that only
  one `finished` row exists.

- **Suggested coverage** labels a gap "issues 5–6 may be in Copperline Vol. 2. Confirm?", with
  **Yes** / **No, it doesn't** on the item page and **Yes, … has issues 5–6** on the card.
- **Suggestions from Metron:** a collected comic volume is now also asked of Metron (alongside
  the book sources, which still rate it). The issue list for its number is filtered to series
  Metron types as trade paperback, hardcover, graphic novel or omnibus. Then the volume's own
  details give its `reprints` ("Series (Year) #N", format confirmed in Mokkari's tests), turned
  into ranges of a series the owner has something of. A single issue's search now **leaves
  collected series out**, which removes one cause of the ties in the owner's test (a trade
  paperback "#1" next to the single issue "#1"). `MATCH_VERSION` 8: re-scored from the cache;
  a few new series-detail requests.
- **One per series with both:** carry on with whichever the owner has been reading (issues or
  collected volumes). If neither, collected volumes come first.
- **Item page → Collects** (comic volumes): what it holds, with Confirm / Not right for
  suggestions, Remove for the owner's own, and "It collects issues of [series] from … to …".
- **Demo:** Copperline issues 1, 2, 4 and 7; Vol. 1 confirmed as 1–4 (issue 3 covered), Vol. 2
  suggested as 5–8 by the demo source ("may be in").

**Needs checking on the owner's PC:** whether Metron's trade paperbacks are found under the same
series name as the issues ("Saga" with the type Trade Paperback) or under their own names ("Saga
TPB"). Both are handled, but only the first is likely to have been seen in Metron's own tests.

## Part 4: merge, split and undo (§11.4, scenarios 13 and 19)

- **Merge** (`lib/operations.ts`): the preview lists only what conflicts, per group that moves
  together (progress with its dates, rating, note, triage, your title, kind, series, match…),
  showing both values. The owner must choose for each conflict; notes and takeaways can keep
  both. What only the other entry has comes along and is listed. The other entry's files,
  places to read, coverage, rejected candidates and missing sources' matches move over. Its id
  becomes an alias, so old links still lead to the book. The shortlist keeps the earlier place.
  One reading stays one reading (a test checks one `finished` row after merging two finished
  copies).
- **Split:** choose files, and whether the reading history **stays or moves as a whole**, never
  copied, so no reading counts twice. The preview lists what stays, what goes, and the history
  that goes with it. At least one file must stay.
- **Undo** (`operations` table, migration `007_operations.sql`): each merge and split keeps the
  exact rows of the items it touched from just before it. Any of the **last 20** can be undone
  back to that state. Undo is refused when the books were edited since (their `updated_at`
  moved), touched by a later merge or split, or are gone. Then the list offers the opposite
  action with a preview: **split them apart** for a merge, **merge them again** for a split.
  Files a later scan added to a merged book find a home again after an undo. Needs review's
  "group as one book" and "they moved" answers are recorded too, so they can be undone.
- **Not in the backup:** a restore clears the undo list, because its snapshots describe the data
  being replaced.
- **Where:** the book's page has "Not all the same book?" (split) and "Same book as another
  entry?" (search, preview, merge, Undo). Needs review rows where both entries have history now
  link to the merge preview, and the page ends with **Recent merges and splits**.

## Part 5: store titles and the store CSV (§14)

- **Add a store book** (Library → Add a store book…): Kindle, Apple Books, Google Play, Kobo,
  GlobalComix or another app. Either **find it online** (the configured sources; the pick
  becomes the book's confirmed match), or **type it in** (title, author, ISBN, series and
  number, kind). A pick that is already a book's confirmed or certain match **joins that book**
  (a second place to read it) instead of making a duplicate (§14: merge only on a confirmed
  match). What the owner types is kept as typed (`title_source = 'owner'`), and a typed ISBN is
  strong evidence for lookups.
- **Ready to read** includes a store book only once the owner ticks "I can read it there now"
  (§13.1: a store name alone doesn't prove it's on the iPad). The book page's **In a store app**
  lists its stores with that tick, Remove, and "Also in…". A book with no files can be removed
  from the library.
- **Store CSV** (Settings): `title, author, store, kind, progress, isbn, series, series_index,
rating, note`; only `title` is needed. The **preview** says, per row:
  - imported before: nothing new;
  - same ISBN as a book you have: the store is added to it;
  - same title and author as a book you have: added there only if ticked;
  - a new book.

  It lists what each row would record and, where the owner already has something different,
  "yours kept". Rows matching nothing are added as unconfirmed books, or skipped.

- **Repeatable** (`import_keys`, migration `008_imports.sql`, backed up): a row is recognised
  by its ISBN, else by normalised title + author + store. A second import adds nothing and never
  overwrites the owner's edits. Owner data only fills what's empty. A "read" with no date is
  finished with the date unknown. Ratings are converted explicitly ("8" or "8/10" out of 10;
  "4/5", "4 stars", "★★★★" doubled); anything else is left out and reported. A byte-order mark
  from Excel is ignored; quoted fields with commas and line breaks are read.
- **Demo:** a Kindle book not yet confirmed readable, and an Apple Books one that is.

## Part 6: Calibre import (§14)

**Checked against Calibre's source (November 2026):**

- `resources/metadata_sqlite.sql`, schema `user_version` 28. `books` has id, title,
  series_index, path and uuid, but no ISBN. ISBNs are in `identifiers`. `ratings.rating` is
  0–10. The `meta` and `tag_browser_*` views call functions only Calibre defines, so only plain
  tables are read.
- `src/calibre/library/custom_columns.py`: `custom_column_N` (id, book, value) for bool,
  datetime, int, float, comments and composite. Value table plus `books_custom_column_N_link`
  for text, enumeration, series and rating.

**What it does:**

- **Read-only.** After a fresh attribute check (an online-only `metadata.db` is refused, §9.5),
  `metadata.db` (and a `-wal` beside it) is copied into the data folder, and only the copy is
  opened, read-only. A test checks the Calibre folder's listing, hash and modified time are
  unchanged.
- **Matching:**
  1. by path, when the Calibre library is inside a scanned folder (`<library>/<book path>/<name>.<format>`);
  2. by ISBN, only when the title or an author agrees too, since an ISBN alone can be another
     edition's.

  Full-hash matching would mean reading Calibre's files, which the app only does inside
  scanned folders; there, path already matches.

- **Facts are kept as a match from the source "Calibre"** (score 1, evidence "the same file, in
  your Calibre library"). They're shown as Calibre's, can be rejected like any match, and a scan
  can't overwrite them. With the match certain, series and order follow (Part 1). Calibre's
  ISBNs are added to the book's identifiers for the online lookups.
- **Owner data only if chosen:**
  - ratings: 0 = unrated, 1–10 kept as they are;
  - a "read" custom column (yes/true/1, or text such as "read");
  - a "date read" column. Calibre's "undefined" year 101 counts as no date.

  It only fills what's empty, and conflicts are shown as "yours kept".

- **Unmatched books** can be added as unconfirmed books ("In another app", note "In Calibre") or
  skipped (the default). The preview suggests scanning the Calibre folder when it isn't inside
  a scanned folder.
- **Repeatable:** recognised by the library's uuid + the book's uuid (`import_keys`).
- Tests use an invented library built with Calibre's own table shapes
  (`server/src/testing/calibre.ts`).

**Needs checking on the owner's PC:** the import on the real Calibre library: how many match by
file and by ISBN, and whether a "read" column exists. Also whether Calibre was open at the time
(the copy should still work; a WAL file is copied if present).

## Part 7: Goodreads and StoryGraph history (§14)

- Settings previews either exported CSV, with matches, possible matches needing confirmation,
  changes, conflicts kept, skipped rows and conversion notes. Cancel saves nothing.
- ISBNs require title or author corroboration. A possible title match is skipped unless confirmed.
  Unmatched read/reading/DNF rows can be kept as **history-only**, never owned or recommended.
  To-read rows without a confirmed library match are skipped, even if the export says owned.

- `import_keys` already belongs to the backup. Repeat imports are a no-op, including if the
  owner has since cleared a rating, note or progress. Backup/restore keeps these keys, dates,
  locations and item ids. No schema change was needed.
- Header shapes checked against the public BookWyrm export fixtures and independently against
  a StoryGraph exporter's conversion script; links and limitations in
  `fixtures/imports/README.md`. Committed records are invented. These public samples do **not**

## Published volumes beyond the library

The owner asked to include this in M4: owning the first two volumes of an ongoing story
should not hide later published volumes. This is separate from the story's final length.

- Hardcover's matched book identifies the series; a second query fetches explicit numbered,
  released primary works. Counts never manufacture a missing range. Compilation memberships
  cannot turn single issues into volumes; ambiguous series, partial/merged works and future or
  unknown publication dates are excluded. Large/truncated responses fail safely.
- Source facts live in migration 009's `series_publications`, included in backup/restore, and
  never create items or ownership. Missing positions are compared with current volume holdings

### Comic runs: "Which run is it?" (2026-11-14)

The owner's Needs review showed comic issues tied between runs of one name (runs of the same
title from different decades, a series against its spin-off with a subtitle, files numbered
"v2"/"v4" or named with a start year). Counts only, no titles: about 885 "same book twice?"
rows, 128 "which book?" ties, most of them comic issues in long runs.

- **Which run is it?** (`lib/runChoice.ts`, `GET/POST /api/review/runs`): tied or unconfirmed
  issues of one series in one folder are grouped; one choice confirms that run's candidate for
  each issue (as "This is it" would), and the rest follow from the run hint.
- **Run key:** issues side by side share a run only when their filenames agree on the series
  volume ("v4") and a joined start year (`runKeyOf`); "Series 01", "Series v2 01" and
  "Series v4 01" in one folder no longer lend each other a run.
- **Spin-offs:** a record that adds a name before its number ("Series: Other Name #5") scores
  as a main-title-only match against "Series #5", and the other way round. A story name after
  the number ("Series, Vol. 6: Arc") is unchanged.
- **Series volume:** Metron's series volume agreeing with a "v4" file settles a tie but stays
  unconfirmed (`SERIES_VOLUME_AGREES`); a different volume drops below review.
- **Metron run searches:** when the plain answer has no issue from the file's run, Metron is
  asked again with `series_year_began` or `series_volume` (at most `METRON_RUN_SEARCHES`, cached).
