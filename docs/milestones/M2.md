# Milestone 2: deep scan and file identity

**Status:** built, and the done-when checks pass in the sandbox and in CI. It still **needs
checking on the owner's machine** (see the end of this note).

## What was built

- **The deep pass (PLAN.md §9.2).** After the light pass, each scan reads inside the files that
  are confirmed `present`, in two phases:
  1. **Reading:** metadata, word and page counts, PDF type, partial hash, then a cover thumbnail.
  2. **Fingerprinting:** the full SHA-256 of every present file, light formats included. This
     runs last, one file at a time, with no time limit, but can be cancelled.

  Each stage is recorded per file with a version (`STAGE_VERSIONS` in `scan/deepPass.ts`). A
  stage is skipped only if it completed at the current version, so a cancelled scan resumes
  where it stopped and failed files are retried. A changed file, or a placeholder that becomes
  present, is read again.

- **Readers (`scan/formats/`, §10):**
  - **EPUB:** OPF title, creators, language, publisher, date, identifiers, subjects,
    description, calibre and EPUB 3 series. The word count comes from the spine, skipping the
    navigation document and repeated pages. Covers come from `cover-image` or `<meta name="cover">`.
  - **CBZ / CBR:** ComicInfo.xml (series, number, volume, writer, penciller, publisher, genre,
    manga and right-to-left). The page count comes from the images, sorted in natural order. The
    cover is the first page. A `.zip`/`.rar` that isn't mostly images is dropped from the
    library and listed in Library health (§9.1).
  - **PDF (pdf.js):** Info and XMP metadata, with junk titles such as "Microsoft Word - …"
    ignored, and a PDF title used only when it agrees with the filename. Also the page count, a
    text-layer word count, and ISBN **candidates** from the first 10 pages (shown as
    "unconfirmed"). The thumbnail is page 1 rendered.
  - **PDF type (§10):** 8 pages are sampled, skipping the cover. **Comic** means mostly
    full-page colour images in a comic shape with little text. **Text** means mostly text.
    **Scanned** means page images with a text layer. Anything else is **uncertain**, with the
    evidence written out. Grey page images with no text stay uncertain on purpose, because they
    could be manga or an un-OCR'd scan. The owner can correct the type on the item page or in
    Needs review. The correction is owner data (`file_user`) and decides the kind.
  - **XML:** a small tolerant reader (`formats/xml.ts`) instead of a dependency. It is
    non-recursive, never reads DTDs and never throws.
- **Limits (§6.1, §20), all in `config.ts`:** 60 s per read (the worker is terminated and
  replaced), 4 GB unpacked, 100:1 compression (checked from the central directory before
  inflating), and 50 megapixels (checked from the image header before decoding). RAR is limited
  to 1 GB, because the reader needs the whole archive in memory. Password-protected files are
  reported as such.
- **Worker pool (§6.1):** `worker_threads`, CPU cores − 1 and at most 4 workers, each with a
  1 GB heap cap. Only one large file (≥ 256 MB) is read at a time across the pool, because the
  heap cap doesn't cover canvas or WASM memory.
- **The content-read guard (§9.5):** `scan/guard.ts` is the only way work reaches the pool.
  Before each read (metadata, cover and full hash separately) it re-checks the file's
  attributes through the platform's long-lived helper. A placeholder or unknown file isn't read,
  and its availability is updated. The light pass's batch listing never authorises a read.
- **Identity (`identify/reconcile.ts`, §9.3, §11.3), after every scan:**
  - **Copies by full hash:** the same file is one item whatever its name. This also carries
    history to a **renamed** file. If both items have history, Needs review tier 1 asks instead.
  - **Conflict check on M1's groups:** copies whose hashes disagree, or a known language,
    abridgment or edition conflict. If the item has no owner data, it is **split automatically**,
    and the old id becomes an alias of the part that kept the primary file. Otherwise it goes
    to **tier 1** and stays grouped.
  - **Candidate moves:** same size and partial hash under a different name, when full hashes
    can't be compared, go to tier 1. A similar name alone never moves anything.
  - **Cross-folder suggestions (rule 3):** the same base name in another folder with a
    different format or size goes to **tier 4**. A suggestion is asked once and stays answered.
  - Facts come from the file's own metadata. The owner's corrections are never touched.
    Editions keep their number in the title ("The Lantern Keepers (2nd edition)").
- **Needs review (first version):** tier 1 (moves, group conflicts, the same file on two items
  with history) and tier 4 (cross-folder suggestions, uncertain PDF types). Each row has plain
  actions: keep history / different files, group / keep apart, split off a file / keep together,
  and "it's a comic / a book / a scan".
- **Library health (§15):** files that couldn't be read, archives that aren't comics, PDFs with
  no text layer, files not yet read or fingerprinted, copies (informational) and skipped file
  types. Errors are kept apart from incomplete files.
- **Scan reminder (§9.7):** a banner for any folder whose last complete scan is over 30 days
  old, with Scan now and "Remind me in a week" (snoozed 7 days). A partial scan doesn't reset
  it.
- **UI:** covers in the Library and on item pages, a "From the file" card, per-file words, pages
  and PDF type with its evidence and a correction, scan progress by phase with an estimate once
  20 files are done, and the deep-scan summary in Settings and Diagnostics.
- **Schema:** migration `002_deep_scan.sql`. Every new column is nullable or has a default.
  **Backups from M1 (version 1) still restore.** The new tables are left empty and the next scan
  fills in the file details. `file_user` and `review_items` are in the backup, and covers are not
  (§16). A missing cover is redrawn by the next scan.
- **Demo:** now made of real generated EPUB, CBZ, CBR and PDF files (all invented). It shows
  covers, a translation split from its original, text / comic / scanned / uncertain PDFs, a
  damaged file, a `.zip` that isn't a comic, a cross-folder suggestion and the scan reminder.

### Dependencies added (no install scripts, no compiler needed)

| Package           | Why                                                                                                                                                                                                                             |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pdfjs-dist`      | Mozilla's maintained PDF reader; its Node build renders through `@napi-rs/canvas`.                                                                                                                                              |
| `@napi-rs/canvas` | Prebuilt binaries for Windows, macOS and Linux, used for covers. One native image library covers both PDF rendering and thumbnails, so `sharp` (the plan's example) wasn't needed. The pixel limit is enforced before decoding. |
| `yauzl`           | Reads a ZIP's central directory and only the entries asked for, straight from the file. Checks declared sizes while inflating.                                                                                                  |
| `node-unrar-js`   | RAR in WebAssembly, so nothing to compile on Windows. Loaded only inside workers, because its runtime installs process-wide error handlers.                                                                                     |

### Benchmark

`npm run benchmark`: 5,000 generated files (40% EPUB with a cover, 30% 12-page text PDF, 20%
12-page CBZ, 10% MOBI) in 417 folders, with the generic adapter (no PowerShell). Measured on an
Intel Xeon 2.3 GHz, 4 vCPU (3 workers), 16 GB, Linux, Node 22.23, local disk:

| Step                                                    | Time                                              |
| ------------------------------------------------------- | ------------------------------------------------- |
| Light scan (listing, names, grouping)                   | 2.0 s                                             |
| Deep pass: reading (metadata, counts, PDF type, covers) | 34.9 s                                            |
| Deep pass: fingerprinting and finishing                 | 9.1 s                                             |
| Whole first scan                                        | 45.9 s                                            |
| Rescan, nothing changed                                 | 3.5 s                                             |
| Library, 1,000 items in one request                     | 29 ms                                             |
| Library page **during** the deep scan (178 requests)    | median 28 ms, 95th percentile 40 ms, worst 153 ms |

**This isn't a Windows or USB-drive number.** The test files are small. Real books are larger
(the owner's comics are 30–250 MB), and the full hash reads every byte. Over USB 3 at roughly
100 MB/s, fingerprinting a few hundred GB would take an hour or more. That's why it runs last,
one file at a time, and resumes. The first real scan will show the actual figure.

## Not in M2 (by plan, or moved)

- Tiers 2–3, search and pick, Defer and Dismiss, and **"confirm all like this"** for tier-1 moves
  arrive with Needs review proper in **M3**. M2 answers rows one at a time. A reorganised folder
  rarely needs them, because same-name moves and renames with the same fingerprint transfer
  automatically.
- Rule 4 (grouping by a corroborated identifier) needs the matching in M3.
- Merging two items that **both** have history needs the conflict preview in **M4**. Until then
  such rows only offer "Keep apart".
- Effort from a readability sample (§12.4) is M3, with durations.
- The full hash is "low priority" by running last and alone. Node can't lower a thread's OS
  priority.

- **Placeholders becoming present** (OneDrive or iCloud): still covered by fakes only, as in M1.
